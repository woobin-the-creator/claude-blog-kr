AI 네이티브 SDLC 플레이북

코드 작성이 더 이상 병목이 아니게 된 시대에, 소프트웨어 개발 수명주기(SDLC)를 단계별로 어떻게 다시 설계할 것인가. Anthropic Applied AI 팀이 고객사와 함께 실제로 돌려 본 관행을 6개 스테이지 · 플레이(play) 단위로 묶은 안내서다.

2026년 8월 21일 · 읽는 데 약 25분 · 카테고리: Enterprise AI, Claude Code 원문: The AI-Native SDLC playbook by Anthropic (claude.com/blog)
안내 — 이 글은 원문의 축자 번역이 아니라, 원문을 읽고 핵심을 한국어로 정리한 요약·해설입니다. 원문의 모든 스테이지·플레이·사이드바를 원문 순서 그대로 빠짐없이 다루고, 원문에 실린 이미지와 링크도 모두 그대로 옮겼습니다. 인용문은 짧게 발췌해 옮겼으며, 설정 예시는 원문이 제시한 템플릿의 뼈대만 옮겼습니다. 정확한 원문 표현과 전체 예시 코드는 위 원문 링크에서 확인하세요.

코드는 더 이상 병목이 아니다

지금 쓰이는 SDLC는 코드를 쓰는 일이 가장 느린 단계였던 시절에 설계됐다. 그 전제 위에서 기획·설계·리뷰·승인 절차가 짜였고, 각 단계의 길이도 그 전제에 맞춰졌다. 에이전틱 AI가 들어오면서 그 전제가 깨졌다. 빌드(build) 단계는 몇 주에서 몇 시간으로 줄어드는데, 그 앞뒤에 붙은 사람 속도(human-speed)의 단계들은 길이가 그대로다.

그래서 새로운 제약은 보안 리뷰, 승인, 정책 점검 같은 것들이 된다. 사람이 만들어 내는 산출량에 맞춰 인원이 편성된 보안팀은, 에이전트가 만들어 내는 코드량을 따라갈 수 없다. 빌드만 빨라지고 나머지가 그대로면 전체 리드타임은 별로 줄지 않는다.

결론은 단순하다. AI가 할 수 있는 일을 기준으로 프로세스를 다시 설계하되, 사람의 감독(oversight)과 거버넌스는 유지해야 한다. 이 글은 그 재설계를 스테이지별로 나눠 놓은 플레이북이다.

AI 네이티브 SDLC란 무엇인가

AI 네이티브 SDLC는 전통 SDLC의 통제 목표(control objective)를 버리지 않는다. 목표는 그대로 두고, 강제 수단(enforcement mechanism)을 바꾼다. 리뷰 회의로 지키던 것을 훅(hook)과 스킬(skill)과 이벌(eval)로 지킨다.

형태도 달라진다. 앞에서 뒤로 흐르는 선형 워크플로가 아니라 순환하는 루프가 된다. 각 스테이지에 AI가 박혀 있고, 스테이지 사이의 인계(handoff)가 자동화된다. 사람이 문서를 옮겨 붙이고 티켓을 넘기던 덜컹거리는 전환이 사라진다.

여섯 스테이지에서 무엇이 바뀌는가

스테이지전통 SDLCAI 네이티브 SDLC
Plan위원회가 요구사항을 모으고, 워크숍과 사인오프로 걸러 낸 뒤 사람이 손으로 문서화한다.Claude가 원 출처에서 직접 페인포인트를 종합해 intent.md에 담는다.
Design분석가가 스펙을 쓰고, 디자이너가 그 스펙을 해석한다.요구사항과 설계를 에이전트와의 한 세션으로 압축하고, 조직 표준이 그 세션을 이끈다.
Build테스트와 코드를 손으로 쓰고, 문서는 개발이 끝난 뒤에 쓴다.테스트와 코드를 AI가 생성하고, 조직 지식은 버전 관리되는 CLAUDE.md로 유지된다.
Test스테이지 경계마다 QA 게이트를 둔다.연속 이벌(continuous evals)이 구현 과정에 짜여 들어간다.
Deploy사람이 모든 줄을 리뷰하고, 거버넌스는 리뷰 사이클 안에서 — 종종 일관성 없이 — 이뤄진다.여러 겹의 에이전틱 리뷰를 쌓고, 사람 리뷰는 규제 대상·핵심 코드에 아껴 둔다.
Maintain사람이 프로덕션을 지켜보며 버그를 찾는다.에이전트가 라이브 배포를 모니터링한다. 통제 범위(control band)를 벗어난 것은 진단되어 다시 파이프라인에 기록된다.
관통하는 한 줄 — 각 스테이지는 버전 관리되는 산출물 하나를 커밋한다. intent.md → spec.md → plan.md → PR → 인시던트 기록. 이 산출물이 감사 추적(audit trail)인 동시에 다음 스테이지의 입력이 된다. 거버넌스를 위해 따로 문서를 만들 필요가 없다는 뜻이다.

플레이를 도입하는 순서

01 Plan — intent.md로 붙잡기

아이디어는 위원회 회의가 아니라 Claude와의 브레인스토밍 세션으로 들어온다. 아이디어를 낸 사람이 자기 말로 intent.md를 쓴다. 사람이 읽을 수 있으면서 기계가 바로 작업에 쓸 수 있는 형태다. 제품 책임자(product owner)가 검토하고 고친 뒤 커밋한다. 몇 주짜리 다듬기 사이클이 사라진다.

실행 절차

  1. Claude에게 문제를 설명한다. 격식 있는 언어는 필요 없다 — 평소 말로 하면 된다.
  2. 구체적인 형태가 잡힐 때까지 함께 브레인스토밍한다.
  3. 조직 템플릿이나 스킬을 써서 intent.md 형식으로 정리해 달라고 한다.
  4. 글쓴이가 잘못 이해된 부분을 직접 고친다.
  5. 공용 저장소에 커밋한다.

intent.md에 들어가는 것: 문제, 제안하는 결과(outcome), 영향받는 사용자, 제약 조건, 미해결 질문.

거버넌스 — 별도 장치가 필요 없다. git 히스토리가 작성자·타임스탬프·수정 이력을 남긴다. 제품 책임자의 승인은 머지 또는 리뷰 종료로 기록된다.

측정 — 선행 지표는 첫 대화부터 intent.md 커밋까지 걸린 시간(몇 주가 아니라 몇 시간이어야 한다). 후행 지표는 2단계까지 살아남는 intent.md의 비율. 커밋 이후 수정이 잦다면 애초에 잘 붙잡지 못했다는 신호다.

02 Design — 요구사항과 설계를 한 세션으로

요구사항 정의와 설계가 프롬프트 한 세션으로 합쳐진다. Claude가 spec.md를 만들고, 조직 스킬(브랜드·보안·컴플라이언스·UX)이 그 과정을 안내한다. 핵심은 타이밍이다 — 정책이 스펙을 쓰는 도중에 적용된다. 몇 주 뒤 리뷰에서 발견되는 게 아니라.

실행 절차

  1. 제품 책임자가 조직 스킬이 로드된 Claude 세션을 열고 intent.md를 붙인다.
  2. 제약 조건을 주면서, 걸리는 지점은 반드시 플래그로 표시하라고 요구한다.
  3. 궁극적으로는 자동화한다 — intent.md가 머지되면 비대화형 잡이 돌아 spec.md PR을 만들어 내게 한다.
  4. 제품 책임자가 스펙을 원래 문제·미해결 질문과 대조해 검토한다.
  5. 플래그된 항목부터 처리한다. 해당 정책 책임자를 부른다.
  6. 위험이 큰 항목은 테크 리드에게 묻는다.
  7. spec.md를 intent.md 옆에 커밋한다.

거버넌스 — 살아 있는 정책이 스펙 작성 중에 읽히고 적용된다. 어떤 버전의 스킬이 쓰였는지가 버전 관리에 남는다. 플래그된 항목은 이름이 있는 정책 책임자에게 라우팅된다.

측정 — 선행: intent.md와 spec.md 커밋 사이 경과 시간. 후행: 빌드 시작 후의 요구사항 재작업 — 첫 plan.md보다 나중 날짜의 spec.md 커밋 수로 센다.

03 Build — 구현과 계획

이 스테이지가 플레이북에서 가장 두껍다. 플레이가 일곱 개 있다.

플레이 — 기본 출발점은 Claude Code 플랜 모드

엔지니어는 플랜 모드로 Claude Code를 연다. 플랜 모드에서 Claude는 코드베이스를 읽되 아무것도 바꾸지 않는다. 승인된 계획은 구현에 들어가기 전에 plan.md로 커밋된다.

  1. 엔지니어가 intent.md와 spec.md를 준다.
  2. Claude가 어떤 파일을 건드릴지, 어떤 순서로 할지, 어떤 테스트를 쓸지를 지목한 구현 계획을 내놓는다.
  3. 엔지니어가 계획을 추궁한다 — 위험은 무엇인지, 다른 선택지는 없는지 — 승인 전에.
  4. 승인된 계획을 plan.md로 커밋한다.
  5. 계획을 참조하며 구현이 진행된다.
  6. 구현이 계획에서 벗어나면, 같은 커밋에서 plan.md도 함께 고친다.
왜 중요한가 — 코드가 생성되기 전에 설계 리뷰가 일어난다는 뜻이다. 전통 SDLC의 설계 게이트가 여기로 옮겨 온다.

플레이 — Claude Code 오토 모드

계획이 승인되고 가드레일이 자리 잡으면, 반복적이고 위험이 낮은 작업은 엔지니어가 매 단계 승인하지 않아도 되는 자율 실행으로 넘길 수 있다. 이때 안전을 지탱하는 것은 사람의 클릭이 아니라 아래에서 설명하는 훅·권한·샌드박스 층이다.

사이드바 — 레거시 시스템과 진실의 원천(source of truth)
이미 Jira, ServiceNow, 요구사항 관리 도구를 쓰고 있다면 어떻게 할 것인가. 원문은 세 가지 선택지를 준다.
  • 저장소가 진실의 원천 — 레거시 시스템은 사본이나 링크만 들고 있는다.
  • 레거시 시스템이 진실의 원천 — 마크다운 파일은 작업용 사본으로 쓴다.
  • 최소한 연결(linkage)은 한다 — 두 시스템을 서로 링크해 두되, 진실의 원천은 두 개인 상태를 감수한다.
어느 쪽이든, 조직은 산출물 유형마다 권위 있는 시스템을 하나로 선언해야 한다. 이게 모호하면 거버넌스가 무너진다.

플레이 — CLAUDE.md

CLAUDE.md는 저장소 수준의 컨텍스트 파일로, 세션 시작 때 읽힌다. 들어가는 것은 빌드·테스트·린트 명령, 컨벤션, 아키텍처, 그리고 Claude가 자주 틀리는 것이다.

# [서비스 이름]

## Commands
- Build: [명령]
- Test:  [명령]
- Lint:  [명령]

## Conventions
- [언어/프레임워크 버전]
- [핵심 데이터 타입 규칙]
- [테스트 요구사항]

## Architecture
- [모듈 구조]
- [외부 연동]

## Things Claude gets wrong
- [자주 저지르는 실수]

처음에는 /init으로 생성하고, 그다음부터는 팀이 관리한다. 운영 규칙 두 가지가 핵심이다.

  • 같은 실수를 Claude가 두 번 반복하면, 그 교정을 CLAUDE.md에 넣는다.
  • 한 페이지를 넘기지 않는다. 코드와 똑같이 버전 관리한다.

플레이 — 조직 지식으로서의 스킬(skills)

스킬은 조직 지식을 실행 가능한 형태로 만든다. .claude/skills 폴더 안에 SKILL.md로 쓴다. 특정 작업에서 트리거되고, 그 안에 정책 강제 내용이 들어간다.

---
name: secure-api-review
description: [트리거 조건]
---
# [제목]

[트리거 상황]일 때:
1. 인증(Authentication): [요구사항]
2. 입력 검증(Input validation): [요구사항]
3. 감사(Audit): [요구사항]
4. 데이터 분류(Data classification): [요구사항]

스킬은 버전 관리되고 정책이 바뀌면 갱신된다. 엔지니어는 새 버전을 자동으로 집어 든다 — 공지를 읽고 각자 반영하는 게 아니라.

플레이 — 빌드 타임 가드레일로서의 훅(hooks)

훅은 스킬 뒤에 놓인 결정론적(deterministic) 층이다. 스킬은 모델에게 "이렇게 하라"고 말하지만, 훅은 그냥 막는다. 훅이 할 수 있는 일:

  • 보호된 경로(protected path)에 대한 편집 차단
  • 포매터·린터 실행
  • 자격 증명(credential)이 새어 나가지 않게 하기

예외 없이 지켜져야 하는 정책이 있는 스킬은 훅으로 뒷받침하라. 다만 훅은 빠르고 범위가 좁아야 한다. 무거운 검사는 PR 단계에 두는 게 맞다.

플레이 — 병렬 세션과 서브에이전트

엔지니어 한 명이 git worktree를 따로따로 두고 Claude Code 인스턴스를 여러 개 돌린다. 각각은 독립적이고, 엔지니어가 전부를 조종한다. 반복적으로 나오는 일(검증기, 단순화기, 리서처)은 서브에이전트에게 맡긴다.

엔지니어의 역할이 바뀐다 — 한 줄기 작업을 직접 하는 사람에서 여러 줄기를 지휘하는 사람으로.

플레이 — Claude에게 피드백 루프를 줘라

세션이 엔지니어가 보기 전에 스스로 자기 작업을 검증하게 만드는 플레이다. 테스트를 돌리고, 빌드하고, 스크린샷을 찍는다. 검사가 통과할 때까지 Claude가 스스로 반복한다.

  • 검증을 명령 하나로 감싼다 (make test 같은 것).
  • 정상 출력이 어떤 모습인지를 CLAUDE.md에 예시로 적어 둔다.
  • 버그 수정이라면 실패하는 테스트를 먼저 쓰고, 그 테스트 파일을 읽기 전용으로 표시한다.
  • 훅으로 피드백 루프 자체가 약해지지 않게 보호한다 — 즉, 테스트를 고쳐서 통과시키는 길을 막는다.

플레이 — CI에서 돌리는 연속 이벌(continuous evals)

스테이지 게이트형 QA의 AI 네이티브 대응물이다. 에이전트 설정이 바뀔 때(CLAUDE.md, 스킬, 훅) 이벌 스위트가 돈다.

  • 최근 작업에서 실제 과제 20~50개를 모으고 각각의 기대 결과를 붙인다.
  • 스케줄에 따라, 그리고 설정이 바뀔 때 비대화형으로 돌린다.
  • 프로덕션 인시던트 하나하나가 영구적인 이벌이 된다 — 회귀 테스트처럼.
  • 설정 변경을 이벌 결과로 게이팅한다.

거버넌스 — 코드 생성 전 플랜 모드에서 설계 리뷰가 이뤄진다. 계획과 그 수정 이력이 승인자와 함께 남는다. 통상적 변경은 엔지니어가, 위험이 큰 변경은 테크 리드나 아키텍트가 승인한다.

측정 — 선행: 첫 구현 패스에서 머지되는 변경의 비율, 계획 승인부터 PR 머지까지 걸린 시간. 후행: 변경당 재작업 사이클 수, 머지된 diff가 커밋된 plan.md와 얼마나 일치하는가.

04 Test — 연속 평가

테스트는 별개의 게이트가 아니라 구현 과정에 짜여 들어간 연속 검증이 된다. 구체적인 내용은 위 Build 스테이지의 "피드백 루프"와 "CI 연속 이벌" 두 플레이가 그대로 이 스테이지의 실행 방법이다.

측정 — 선행: 에이전트가 작성한 변경의 CI 첫 패스 성공률. 후행: PR당 리뷰 시간, 변경 실패율(change failure rate).

05 Deploy — 리뷰와 릴리스 게이팅

Claude가 들어오는 PR을 리뷰하고, 자기가 낸 PR에 달린 리뷰 코멘트도 스스로 처리한다. 모든 PR이 똑같은 리뷰 패스를 받고, 발견 항목은 심각도로 정렬된다. 사람의 주의는 의도(intent)와 위험 판단으로 옮겨 간다. 거버넌스는 에이전트가 행동하는 그 순간에 강제되고, 에이전트는 프로덕션 게이트를 스스로 통과할 수 없다.

플레이 — PR 리뷰 루프 안의 AI

Code Review 매니지드 서비스를 쓰거나, CI에서 claude-code-action을 돌린다. 테크 리드는 리뷰 정책을 REVIEW.md로 글로 써 둔다.

# Review instructions

## Passes
- 버그/로직: [설명]
- 보안/취약점: [설명]
- 컴플라이언스: spec.md · plan.md · 설계 원칙과 대조

## What "Important" means here
[이 저장소에서 Important의 정의]

## Cap the nits
[사소한 지적의 상한]

## Do not report
[아예 보고하지 않을 것들]

운영 규칙은 이렇다.

  • 브랜치 보호로 코드 오너 승인을 요구한다. 리뷰 발견 항목이 자동 승인을 만들어 내지 않는다.
  • 리뷰어가 코멘트에 @claude를 붙이면 Claude가 고쳐서 푸시한다. PR 스레드가 요청과 변경을 모두 기록한다.
  • 리뷰 발견 항목은 CLAUDE.md로 되먹임된다.
  • 월 단위 튜닝 — 발견 항목에 평점을 매겨 리뷰어를 개선하고, nit(사소한 지적)의 양에 상한을 둔다.

거버넌스 — 코드를 쓴 에이전트가 그 코드를 승인할 수 없다. 리뷰 정책은 모두에게 균일하게 적용된다. 발견·수정·평점이 PR 히스토리에 남는다.

측정 — 선행: 첫 리뷰까지 걸린 시간(분 단위여야 한다), 에이전트가 해결한 리뷰 코멘트의 비율. 후행: 머지 전에 잡힌 결함·취약점 대 프로덕션까지 새어 나간 것.

플레이 — 승인 게이트로서의 훅

훅은 막기만 하는 게 아니라 행동 전에 사람의 승인을 물어보고, 승인될 때까지 멈춰 있을 수도 있다. 가장 명확한 사례가 릴리스 게이트다. 마이그레이션 보호, 테스트 파일 보호에도 쓴다.

#!/bin/bash
# 릴리스 승인 없이는 프로덕션 배포를 막는다
cmd=$(jq -r '.tool_input.command' < /dev/stdin)
if [[ "$cmd" == *"production"* ]]; then
  if [ -z "$RELEASE_APPROVAL" ]; then
    echo "[승인 경로를 안내하는 메시지]" >&2
    exit 2
  fi
fi
exit 0

훅으로 살아남는, 미리 정의된 승인들: 변경 관리 사인오프, 릴리스 승인, 보호된 경로 편집.

  • 플랫폼 엔지니어가 게이트를 훅으로 표현한다. 훅은 허용(allow) · 질의(ask) · 차단(block) 중 하나를 할 수 있다.
  • 팀 훅은 git에 들어간 .claude/settings.json에 둔다. 협상 불가능한 훅은 매니지드 설정에 둔다.
  • 차단은 스스로를 설명해야 한다 — 왜 막혔는지와 승인받는 경로를 함께 알려 줘야 한다.

거버넌스 — 게이트 조건이 매번, 모두에게 강제된다. 허용/차단 판단이 타임스탬프와 함께 로깅된다.

워크드 예시 — 규제 산업 기업을 위한 매니지드 설정
플랫폼 팀이 MDM이나 관리자 콘솔로 통제하는 형태의 예시다. 골자는 다음과 같다.
  • 파일·자격 증명 접근을 거부(deny)하고, 안전한 명령만 허용(allow)한다 (Read(.env*)·WebFetch 거부, Bash(git *)·Bash(make test) 허용 같은 식).
  • 샌드박스로 OS 수준 격리 + 네트워크 도메인 허용목록 + 자격 증명 필터링을 건다.
  • 플러그인 마켓플레이스를 통해 승인된 플러그인만 쓰게 한다.
  • 최소 버전을 강제하고, 오래된 배포는 거부한다.
전부 버전 관리되고 감사 가능하다. 자세한 키는 code.claude.com/docs/en/settings에 있다.

플레이 — CI/CD 연동과 배포

Claude가 파이프라인 안에서 비대화형으로 돌면서 판단이 필요한 단계를 맡는다.

- name: [작업 이름]
  if: [조건]
  run: >
    claude -p "[프롬프트]"
  • 샌드박스 실행 + 범위가 좁혀진 자격 증명.
  • 배포 도구는 MCP를 통해 노출한다.
  • 환경별로 자율성 등급을 나눈다 — dev는 자유 배포, staging은 중간, prod는 훅 게이트.
  • 롤백이 가장 많이 연습된 경로여야 한다. staging에서 정기적으로 실제로 돌려 본다.

거버넌스 — 에이전트는 프로덕션 게이트 앞까지만 행동하고 그 게이트를 넘지 못한다. 브랜치 보호가 에이전트의 결과물을 PR로 만들고, 환경별 권한 등급이 권한 상승을 통제한다.

측정 — 선행: 사람을 호출하지 않고 분류된 파이프라인 실패의 비율. 후행: DORA 지표(배포 빈도, 리드 타임, 변경 실패율, MTTR).

06 Maintain — 루프 닫기

마지막 스테이지는 사람이 호출 경로에 없는 자율 루프다. 모니터링 임계 이탈, 티켓, Slack 메시지, 스케줄 같은 이벤트가 트리거가 된다. Claude가 진단하고, 게이트된 경로를 통해서만 행동하며, 발견 내용을 intent.md로 쓴다. 그 작업은 1단계로 다시 들어가 전체 SDLC를 거친다. 루프가 닫힌다.

플레이 — 유지보수와 루프 닫기

결정론적 스크립트가 프로덕션을 지켜보다가 통제 범위(control band)가 깨지면 Claude를 호출한다. 중요한 설계 결정이 하나 있다 — 모니터링은 전적으로 결정론적으로 유지한다. 탐지에는 모델이 관여하지 않는다.

대응 등급은 버전 관리되는 설정에 적는다.

metric: [지표 이름]
baseline: rolling_30d
rules: western_electric
tiers:
  1sigma: { action: log }                      # 로그만 남긴다
  2sigma: { action: diagnose, tools: "..." }   # Claude가 읽기 전용으로 진단
  3sigma: { action: propose, routes: [...] }   # Claude가 게이트된 경로로 행동
  • 트리거 층: 스케줄된 워크플로, 웹훅, 또는 Cron 잡.
  • Claude는 상태 없이(stateless), 비대화형으로 CI 스텝이나 Agent SDK 서비스로 돈다.
  • 에이전트가 진단을 intent.md로 쓴다 — 이상 현상, 증거, 제안하는 결과, 영향받는 시스템, 미해결 질문.
  • 서비스 오너나 온콜 담당자가 그 큐를 분류(triage)한다. 제품 쪽 발견은 제품 책임자에게 라우팅한다.
  • 수정이 배포되면 그 인시던트에 대한 이벌을 추가한다. 영구 회귀 테스트가 된다.

거버넌스 — 등급 경계가 버전 관리된 설정에서 강제된다. 호출·발견·분류가 타임스탬프와 함께 로깅된다. 서비스 오너가 분류하고 승인한다. 변경은 평소의 PR 게이트를 그대로 거친다. 런북(runbook)은 미리 승인돼 있다.

측정 — 선행: 범위 이탈부터 intent.md가 분류 큐에 올라오기까지의 시간(예전의 "포스트모템 액션까지 걸린 시간"과 비교하라). 후행: 발견 중 실제 머지된 수정으로 이어진 비율, 같은 유형의 인시던트 재발 횟수.

플레이 — Claude Tag로 온콜 서기

인시던트는 Slack이나 Teams로 들어온다. Claude Tag는 Claude를 채널의 구성원으로 만든다.

  • 모든 인시던트가 1차 대응(first-responder) 커버리지를 받는다. 그 대응 자체가 루프와 기억의 일부가 된다.
  • 대화와 조직 지식이 채널 안에 그대로 남는다.
  • 채널에 있는 누구나 대응을 이끌 수 있다. 조사가 실시간으로 진행된다.
  • MCP를 통해 Claude가 지표가 기준선으로 돌아왔는지 직접 확인하고, 포스트모템을 버전 관리되는 교훈 파일에 쓴다.
  • 티켓도 같은 방식으로 분류된다. 작은 수정은 리뷰 게이트를 거쳐 PR이 되고, 큰 작업은 intent.md가 된다.

맺는 생각

지금의 모델과 하니스(harness)는 코드 생성만이 아니라 SDLC 전체를 바꿀 수 있는 수준에 와 있다. 그리고 그 변화는 사람의 판단을 중심에 남겨 두는 방식으로 이뤄질 수 있다 — 대기업이 요구하는 거버넌스와 규제 요건을 만족시키면서.

이 플레이북은 Anthropic Applied AI 팀이 고객사와 함께 실제로 해 온 것들을 모아 놓은 것이다. 원문의 마지막 문장이 전체를 요약한다.

루프는 계속 돈다. 사람의 판단은 그 위에 남는다.
(The loop keeps running. Human judgement stays above it.)
