# 사용자 직접 포스팅 + AI 첨삭 — 확정 설계

## Problem

지금 이 사이트에 글이 올라가는 유일한 경로는 **커밋·푸시**다:

```
브라우저/스킬 → Supabase 큐(cbk_yt_queue) → launchd 폴링 → claude -p
  → 파일 생성 + posts.js 수정 → git push → Actions → Pages
```

실패 지점 6개, 지연 수 분, 맥이 꺼지면 정지. 그리고 이 구조는 **기능이 늘 때마다 큐 종류나 워커 분기가 하나씩 는다** — `cbk_yt_queue`는 이름은 유튜브인데 이미 웹 문서까지 받고 있고(`supabase/schema-youtube-queue.sql:11`), 워커는 URL 모양으로 `case` 분기를 친다(`.pipeline/youtube_worker.sh:96`).

여기에 두 가지를 얹어야 한다:
1. 내가 직접 글을 쓰는 기능
2. 글이 새로 올라가거나 수정될 때 AI가 첨삭하는 기능

큐 위에 그대로 얹으면 큐 종류가 4개가 된다. 사용자는 **"커밋해야 글이 올라가는 구조 자체를 없애고, GitHub은 원래 메인 기능인 코드 변경이력 저장소로만 쓰겠다"**고 판단했다.

## Goals

- 글 발행에서 **커밋을 완전히 제거한다.** 웹에서 쓰고 누르면 즉시 읽힌다.
- 큐 테이블과 폴링 워커를 **은퇴시킨다.**
- 포스트 추가·수정이 **이벤트로 첨삭을 트리거**한다. 첨삭은 발행을 막지 않는다.
- 카탈로그 소스를 **하나로** 만든다 (지금은 `posts/assets/posts.js` 손편집).
- 기존 URL(`/posts/<slug>.html`)과 북마크·`wiki/sources/*.md` 링크 그래프를 깨지 않는다.

## Non-goals

- 로그인·다중 사용자 — `sync_key` 단일 비밀 모델 유지
- SSR / 검색엔진 노출 — Pages 정적 셸 + 클라이언트 렌더를 유지하므로 SEO는 포기한다
- 기존 79개 번역 포스트의 웹 편집 — 읽기 전용
- 첨삭 에이전트가 글을 직접 수정하는 것 — 지적만 한다
- 기존 미디어 79MB를 Supabase Storage로 옮기는 것
- 미디어가 git에 계속 쌓이는 문제(현재 79MB) — 인지하되 이번 범위 밖

## Decisions

| # | 결정 | 고른 것 | 근거 |
|---|------|---------|------|
| 1 | 포스트 저장소 | **Supabase `cbk_posts`** (본문 텍스트) | 사용자 선택. 커밋을 발행 경로에서 제거하는 유일한 방법. 본문 79개 합계 1.5MB(평균 19KB)로 무료 DB 500MB 한도의 0.3% — 용량 리스크 없음 |
| 2 | git의 역할 | **코드 + 야간 콘텐츠 스냅샷** | 기본값. 사용자 표현("변경이력 저장소")과 일치. Supabase 계정 상실 시 아카이브 보존 + 에이전트의 파일 `grep` 유지 |
| 3 | 기존 미디어 79MB | **Pages에 그대로.** 본문 `<img src>`가 Pages 절대 URL을 가리킨다 | 사용자 선택. Supabase 용량·egress 0. 미디어는 AI 파이프라인 산출물이라 내 글쓰기 경로에 영향 없음. 내가 쓴 글의 새 이미지만 Storage로 |
| 4 | 첨삭 실행 위치 | **맥 상주 리스너가 헤드리스 에이전트 스폰** | 사용자 선택. Claude Code 구독 과금 유지 |
| 5 | 첨삭 트리거 | **Supabase Realtime 구독** (폴링 아님) | 기본값. 방금 없앤 지연을 되살리지 않음 |
| 6 | 에이전트 지정 | `CBK_REVIEW_CMD` 환경변수 (기본 `claude -p`) | 기본값. 사용자가 hermes를 언급 — 교체 가능해야 함 |
| 7 | 첨삭 타이밍 | **자문.** 발행을 막지 않고 나중에 리뷰로 붙음 | 사용자 선택 |
| 8 | 첨삭 깊이 | 문장·구성 + 글 안에서 판단 가능한 오류. 확신 없는 사실 주장만 검색 확인 | 기본값. 전건 검색은 글당 수 분 + 오탐 |
| 9 | 편집 범위 | **내가 쓴 글만.** 번역 포스트는 읽기 전용 | 사용자 선택. 에디터가 마크다운 하나만 다루면 됨 |
| 10 | 옛 URL 보존 | **Pages `404.html` 폴백** — JS가 경로를 읽어 DB에서 렌더 | 기본값. 정적 호스트에서 파일 없이 경로 라우팅하는 유일한 방법 |
| 11 | 리뷰 가시성 | `sync_key` 있을 때만 렌더 | 기본값. 공개 리포지만 개인 선호 로그 |

## Acceptance criteria

1. `write.html`에서 마크다운으로 글을 쓰고 발행하면, **git 커밋 없이** 그 글이 인덱스·사이드바·보관함·직접 URL에서 읽힌다.
2. 발행/수정 후 맥 리스너가 폴링 없이 깨어나 에이전트를 스폰하고, 첨삭 결과가 `cbk_reviews`에 쌓인다.
3. 첨삭이 진행 중이어도 글은 이미 공개돼 있다(자문).
4. 리뷰 지적마다 **반영함/무시**를 눌러 닫을 수 있고, 그 상태가 기기 간 동기화된다.
5. 기존 `/posts/<slug>.html` URL 79개가 전부 살아 있다.
6. `posts/assets/posts.js`가 사라지고, 카탈로그를 읽는 곳(`index.html`, `library.html`, `nav.js`)이 DB 한 소스만 본다.
7. 번역·유튜브 스킬이 `scripts/publish.mjs`를 통해 글을 올리고, 더 이상 `posts.js`를 손편집하지 않는다.
8. 야간 스냅샷이 `content/*.md`로 DB를 덤프해 커밋한다.
9. `cbk_yt_queue`와 `.pipeline/youtube_worker.sh`의 폴링 루프가 제거된다.
10. `tests/`가 전부 통과한다.

## Rejected alternatives

- **브라우저가 GitHub Contents API로 직접 커밋** — 발행 경로를 6단계→2단계로 줄이지만 **여전히 커밋이 발행 조건**이다. 사용자가 없애려는 것이 바로 그 조건. (+ 브라우저에 리포 쓰기 PAT 보관 필요)
- **Supabase 큐 + 맥 워커 유지 (youtube_worker.sh 패턴 복사)** — 새 비밀값이 없다는 장점뿐. 6단계·수 분 지연·맥 의존을 그대로 두고, 기능마다 큐가 느는 문제를 재생산한다.
- **로컬 마크다운 파일 + 빌드 스크립트** — "페이지에서 쓴다"를 못 만족한다. 맥 앞에서만 글을 쓸 수 있음.
- **포스트를 git에 유지 (초기 권고안)** — 스킬 3종이 파일 기준으로 돌고 아카이브가 내구적이라는 장점이 있었으나, 커밋-발행 결합을 못 끊는다. **결정 2의 야간 스냅샷이 이 장점을 되찾는다.**
- **미디어까지 전부 Supabase Storage** — git에 코드만 남는 순수한 형태. 300개 파일 이관 + 본문 URL 일괄치환 비용에 비해 얻는 게 적고, 무료 Storage 할당과 월 10GB egress를 쓰기 시작한다.
- **신규 글만 DB, 기존 79개는 파일 유지** — 변경 범위는 가장 작지만 카탈로그가 둘로 갈라져 지금 아픈 분리를 재생산한다.
- **첨삭을 GitHub Actions에서 실행** — push 이벤트가 그대로 트리거라 우아하지만 `ANTHROPIC_API_KEY` 과금이 Claude Code 구독과 별도로 붙는다. (커밋이 발행 경로에서 빠지면서 push 이벤트 자체가 사라져 부차적으로도 탈락)
- **브라우저가 Anthropic API 직접 호출** — 실시간 첨삭은 가능하나 발행된 글의 수정 이벤트를 놓친다.
- **첨삭 게이트(승인해야 발행)** — 틀린 글이 공개되지 않지만 왕복 2번이 되어 즉시 발행의 이점을 상쇄한다.
- **자동 수정 + 노트** — 손이 덜 가지만 내 문장을 내가 안 본 사이 에이전트가 바꾼다.

## Provenance

- 2026-09-01 인터뷰 세션(`/kick-off`). 사용자가 라운드 1에서 초기 권고안(웹→큐→워커)을 기각하며 "커밋해야 글이 올라가는 구조 자체를 없애고 싶다"고 판단 방향을 뒤집었다.
- 측정 사실: 포스트 본문 79개 = 1.5MB(평균 19KB, 최대 60KB) / `posts/assets` = 79MB, 300개 파일, 10MB 초과 파일 없음.
- Supabase 무료 한도: DB 500MB 초과 시 read-only, egress 10GB/월(5 cached + 5 uncached), 파일당 50MB.
